# 10s 刷新维持 60fps，怎么做性能指标监控，怎么验证优化效果？

地图上常驻 300-500 个标记，虽然数据每 10 秒才推一次，但用户平时拖拽缩放地图时，画面必须稳定在 60fps 不掉帧；而 10 秒一次的数据更新，也要做到"只更新变化的点、不阻塞主线程、不造成肉眼可见的卡顿"。

我主要用 Chrome 的 Performance 面板做监控和验证：实时 FPS 看拖拽掉不掉帧，录火焰图看主线程的长任务，Rendering 面板看合成层和重绘区域。对于"10 秒刷新"的数据更新，我在 `addBoatMarkers` 前后用 `performance.now()` 打点，量化这一次 diff 的耗时，目标是远小于一帧的 16.6ms。

验证优化效果用对照法：先录一份"300-500 点 + 拖拽 + 10s 刷新"的基线，记下 FPS、长任务、DOM 数量；然后**每次只上一个优化、再录一次对比**。比如视口剔除上线后，挂载的 marker 从 500 降到视口内几十个，拖拽 FPS 从掉到 20-30 恢复到稳定 60；增量 diff 上线后，10 秒刷新耗时从全量重建的几百毫秒降到十几毫秒，不再造成肉眼可见的卡顿。



# 基于 Haversine 球面距离自研手动圈选聚合：用户在地图上拖拽画圆，实时筛出圈内密集船舶并以列表面板逐条展示、定位。

Haversine就是 算地球表面上两个经纬度点之间的真实距离（多少米）

，

你手上有两艘船，只知道经纬度，比如：

- A 船：(121.5, 31.2)
- B 船：(121.6, 31.3)
想算它俩离多远。最直觉的想法是"拿两个数相减，再按比例换算成米"。但这 是错的 ，因为：

1. 地球是圆的 ，不是一张平纸。两个点在地图上画条直线，那是"投影后的假距离"。
2. 同样 1 度经度，在不同纬度对应的实际米数不一样 。赤道上 1 度经度约 111 公里；到了高纬度（靠近极地），1 度经度实际很短。所以你没法用一个固定比例去乘。
所以需要用 球面距离公式 ，把"地球是圆的"这件事算进去。





Haversine它输入两个点的经纬度，输出这两点在**地球表面走最短路径（叫"大圆距离"）**的真实米数。

它就是一段三角函数公式


结合拖动，mousedown 定圆心 → mousemove 用 Haversine 算距离实时改半径画临时圈 → mouseup 落定成固定圈 → 遍历船算距离筛出圈内船弹列表。



# CSS 动画替代 JS 动画，在地图标记场景下优势是什么

CSS 动画用合成器线程 + GPU，`transform/opacity` 不触发重排重绘，不占 JS 主线程，多标记循环动画下比 JS 定时器更省 CPU、更流畅、更省内存；但前提是标记是 DOM 元素，引擎绘制到 canvas 上的标记用不了 CSS，只能回退 JS。

# 态势大屏的自适应适配方案是怎么做的

我监听 window 的 resize 事件，容器宽高一旦变化就调天地图的 checkResize()，让地图重新读取容器尺寸、重新对齐瓦片和中心点，避免出现瓦片没铺满或中心点偏移。这个场景包括用户拖拽浏览器窗口、进入/退出全屏、以及侧栏面板展开收起导致地图容器被挤变形。
UI 元素用 vw/vh 加媒体查询做流式布局。
